# BODA VMS MLOps

검사 모델의 생애주기를 웹에서 다루는 플랫폼입니다. 상위 설계 문서(`docs/MLOps 개발 문서.md`)의
**Phase 1(모델 레지스트리·배포)**, **Phase 2(데이터 관리)**, **Phase 3(학습 워커)**,
**Phase 4(브라우저 라벨링)**, **Phase 5(모니터링·재학습)** 를 구현합니다.
이미지를 웹에 올려 라벨을 붙이고, 버전을 떠서 학습을 돌리고, 결과를 라인에 배포하고 롤백하는 한 바퀴가 브라우저에서 돕니다.
라벨링은 손으로 그리는 것 외에 SAM 클릭 분할도 씁니다. 배포한 뒤에는 라인의 검사 이력을 당겨 와
모델 버전별로 견주고, 나빠진 것에는 지난 설정 그대로 재학습을 열어 줍니다.

현장 검사 런타임(VMS·VisionSetup)은 그대로 SDK 역할을 유지합니다. 이 플랫폼은 모델을 만들고 내려보내는 상위 계층입니다.

## 구성

```
BODA.VMS.MLOps.slnx
├── src/BODA.VMS.MLOps.Core        순수 로직 — 도메인 열거형·model:// 참조·작업 상태 머신
│                                  ONNX 규약 판별·하이퍼파라미터 화이트리스트·라벨 도형·내보내기 작성기
├── src/BODA.VMS.MLOps.Contracts   서버 ↔ 워커 ↔ 브라우저 공용 DTO
├── src/BODA.VMS.MLOps.Server      관리 서버 (ASP.NET Core 8, SQLite WAL, SignalR) — 화면도 함께 호스팅
├── src/BODA.VMS.MLOps.Client      관리 화면 (Blazor WebAssembly + MudBlazor)
├── src/BODA.VMS.MLOps.TrainWorker 학습 워커 (Windows 서비스, GPU PC)
├── tests/BODA.VMS.MLOps.Tests     xUnit 299개 — 규약·상태 머신·API·워커 프로토콜·E2E
├── scripts/                       학습 스크립트(VMS 리포와 동일 규약) + 진단·허용 목록·가짜 스크립트
└── docs/                          상위 설계 문서 3종
```

외부 의존은 `VMS.Core.Contracts` NuGet 패키지 하나입니다. VMS 런타임과 공유하는 규약 계층으로,
ONNX 메타데이터 리더, 검출 규약 판별, 학습 stdout 프로토콜 파서가 들어 있습니다.
VMS 리포에서 `tools\pack-contracts.ps1` 로 만들어 `D:\Repo\nuget-local` 에 놓으면 `nuget.config` 가 집어 갑니다.

## 실행

```bash
# 규약 패키지 준비 (VMS 리포에서 1회)
D:\Repo\VMS\tools\pack-contracts.ps1

dotnet build BODA.VMS.MLOps.slnx
dotnet test  BODA.VMS.MLOps.slnx

# 서버 + 관리 화면 (화면 http://localhost:5310 · API 문서 /swagger)
dotnet run --project src/BODA.VMS.MLOps.Server

# 워커 (GPU PC)
BODA.VMS.MLOps.TrainWorker.exe configure --server http://<서버>:5310 --token wk_...
BODA.VMS.MLOps.TrainWorker.exe
```

서버는 시작할 때 `Jwt:Key` 가 32자 이상인지 확인하고, 없으면 부팅을 멈춥니다.
개발은 `dotnet user-secrets set "Jwt:Key" "<32자 이상>"`, 운영은 환경변수 `Jwt__Key` 를 씁니다.
BODA.VMS.Web 과 같은 키·발급자를 쓰면 기존 로그인 토큰이 그대로 통합니다.
스키마는 마이그레이션으로만 바꿉니다. 서버는 부팅할 때 밀린 마이그레이션을 적용합니다.

## 화면 디자인

산업용 비전 솔루션 웹(세이지 SAIGE VISION 등)의 화면 언어를 참고했습니다. 요지는 셋입니다.

- **흰 바탕에 거의 검은 글자.** 대비를 세게 두고 회색조로 층을 나눕니다.
- **강조색은 하나만, 아주 적게.** `#FF4052` 를 지금 누를 것과 지금 켜져 있는 것에만 씁니다.
- **모서리를 죽입니다.** 반경 2px. 그림자 대신 1px 실선으로 구획을 나눕니다.

검사 화면은 사진과 라벨이 주인공이라 UI 가 색을 가져가면 안 됩니다. 같은 이유로 라벨 색 팔레트는
파랑부터 시작합니다. 빨강이 앞에 있으면 "지금 고른 UI 요소" 와 "라벨" 이 같은 색이 되어 눈으로 갈라지지 않습니다.

화면 머리말은 작은 강조색 라벨 + 굵은 제목 + 한 줄 설명으로 통일했습니다 (`PageHeader`).
색·서체·모서리 값은 `MlopsTheme.cs` 한 곳에 있습니다.

개발 서버에서 `Auth:EnableDevTokens` 가 켜져 있으면 역할별 버튼으로 바로 들어갈 수 있습니다.

| 모델 · 모델 상세 | 계열 생성, ONNX 업로드, 버전 표, 스테이지 승격, 버전 상세 드로어(메타데이터·지표·이력) |
| 레시피 바인딩 | 도구에 모델 연결, 운영 추종/버전 고정, 롤백, 이력 |
| 데이터셋 · 라벨링 | 데이터셋 생성, 이미지 업로드, 격자 조회·필터, 분할 지정, 버전 만들기 |

| 학습 작업 · 상세 | 작업 제출(서버 화이트리스트 기반 하이퍼파라미터), 실시간 진행률·로그, 취소·재실행, 재현성 레코드 |
| 데이터셋 버전 | 스냅샷 목록, 내보내기 zip 다운로드, 밖에서 만든 zip 업로드 |
| 워커 | 상태·GPU·진단, 토큰 발급/재발급, 비활성화 |

실시간 로그는 SignalR 로 받고, 웹소켓이 막힌 환경에서는 자동으로 폴링으로 내려갑니다.

## 데이터 관리와 라벨링 (Phase 2·4)

이미지는 SHA-256 으로 한 벌만 저장합니다. 같은 파일을 다시 올리면 기존 레코드를 돌려주고,
거의 같은 사진은 지각 해시로 찾아 알려 줍니다. 지울지는 사람이 정합니다.

데이터셋은 이미지를 복제하지 않고 참조로만 담습니다. 한 장이 여러 데이터셋에 들어갈 수 있고,
라벨은 데이터셋마다 따로 붙습니다. 클래스 집합이 다르기 때문입니다.

라벨 좌표는 0~1 정규화입니다. 축소본으로 그리다 원본으로 바꿔도 값이 변하지 않고,
나중에 이미지 해상도가 달라져도 라벨이 그대로 유효합니다.

작업 유형이 쓸 수 있는 도형을 정합니다. 검출은 사각형과 폴리곤, 세그멘테이션은 폴리곤,
분류와 이상탐지는 이미지당 클래스 하나, OCR 은 사각형과 텍스트입니다. 서버와 화면이 같은 규칙을 씁니다.

이미지 한 장은 한 사람만 고칩니다. 잠금은 만료 시각으로 관리해 브라우저가 그냥 닫혀도
정해진 시간이 지나면 다른 사람이 이어받습니다. 저장할 때마다 잠금이 연장됩니다.

버전을 뜨면 이미지 목록과 라벨과 분할이 매니페스트로 굳습니다. 해시는 내용에서만 나오므로
같은 내용이면 언제 떠도 같은 값이고, 그 값이 학습 작업의 재현성 레코드에 남습니다.
내보내기 zip 은 처음 요청될 때 만들어 캐시합니다.

### SAM 보조 라벨링

객체를 클릭하면 그 경계를 폴리곤으로 만들어 줍니다. Enter 로 확정해야 라벨이 되고,
그 전까지는 점선 미리보기일 뿐입니다.

클릭 한 번의 뜻은 대개 애매합니다. 사선 위를 집었을 때 사선만 원한 것인지 그것이 놓인 판을
원한 것인지 모델은 알 수 없습니다. 그래서 다루는 방법을 넷 둡니다.

| 하는 일 | 조작 |
|---|---|
| 더 크게·더 작게 해석한 후보로 넘기기 | Tab (Shift+Tab 은 반대) |
| 빼고 싶은 곳 지정 | Shift+클릭 또는 오른쪽 클릭 |
| 마지막 점 무르기 | Backspace |
| 확정한 뒤 경계 손보기 | 꼭짓점 끌기 · 선을 눌러 꼭짓점 넣기 · Ctrl+클릭으로 빼기 |

두 번째 클릭부터는 직전 마스크를 함께 넣어 다듬습니다(공식 SamPredictor 와 같은 방식).
이게 없으면 배경 점을 찍어도 잘 듣지 않습니다.

가려져 두 조각이 난 물체는 클릭한 조각을 돌려주고, 조각이 더 있으면 그 수를 알려 줍니다.
나머지 조각은 따로 클릭해 라벨을 하나 더 붙이면 됩니다.

모델은 MobileSAM(Apache 2.0)이고 저장소에 넣지 않습니다.

```bash
# 1) 인코더·디코더 준비 — VMS 리포에서 복사하거나 직접 내보낸다 (.onnx 와 .onnx.data 가 한 세트)
cp VMS.DeepLearning/models/sam/mobile_sam_*.onnx* src/BODA.VMS.MLOps.Server/models/sam/
python scripts/export_mobile_sam.py --output src/BODA.VMS.MLOps.Server/models/sam

# 2) 후보 여러 개를 쓰려면 디코더에 출력을 하나 더 연다 (pip install onnx 만 있으면 된다)
python scripts/patch_sam_decoder_multimask.py \
    --input  src/BODA.VMS.MLOps.Server/models/sam/mobile_sam_decoder.onnx \
    --output src/BODA.VMS.MLOps.Server/models/sam/mobile_sam_decoder_multi.onnx
```

2번을 건너뛰어도 동작합니다. 그때는 모델이 고른 해석 하나만 나오고 Tab 이 할 일이 없습니다.
경로는 `appsettings.json` 의 `Sam:` 절이고 상대 경로는 설치 폴더 기준입니다.
파일이 없으면 기능만 꺼진 채 서버가 그대로 뜨고, 라벨링 화면은 SAM 버튼만 숨깁니다.
손으로 그리는 길은 언제나 열려 있습니다.

### Active Learning

데이터셋 화면의 **[모델로 미리 채우기]** 로 후보 모델을 미라벨 이미지에 돌립니다.
붙는 것은 초기 라벨이고 상태는 '작업 중' 입니다 — 사람이 확인하고 고쳐야 완료가 됩니다.
사람이 이미 손댄 이미지는 건드리지 않습니다.

함께 기록되는 것이 **불확실도**입니다. 라벨링 큐가 이 값이 큰 것부터 내보내므로,
사람은 모델이 헷갈려 하는 사진부터 봅니다. 규칙은 둘입니다.

- 아무것도 못 찾았으면 가장 애매합니다 (1.0). 모델이 모르는 그림이라는 뜻입니다.
- 찾았으면 그중 **가장 확신 없는 상자**가 그 사진을 대표합니다. 0.99 짜리 하나와 0.3 짜리 하나가
  함께 있으면 그 0.3 이 문제이기 때문입니다.

지금은 **검출만** 지원합니다 (YOLO · D-FINE). 분류·이상탐지·OCR 은 후처리 규약이 저마다 달라,
확인하지 못한 코드를 늘리는 대신 이유를 말하며 거절합니다.

### 설계 판단

**SAM 은 인코더와 디코더를 모두 서버에서 돌립니다.** 설계 문서는 디코더를 브라우저
onnxruntime-web 으로 돌리는 그림이었습니다. 그렇게 하면 첫 클릭 전에 런타임 약 10MB 와
디코더 약 33MB 를 받아야 하고, 사진마다 임베딩 4MB 를 따로 내려보내야 합니다.
폐쇄망에서 사진 한 장 볼 때마다 4MB 를 더 보내는 대신, 사내망 왕복 한 번으로 2KB 짜리
폴리곤만 받습니다. 무거운 쪽은 인코더인데 그것은 어느 쪽 설계에서든 서버 몫입니다.
브라우저 디코더로 옮기고 싶어지면 임베딩을 그대로 내려보내는 엔드포인트만 더하면 됩니다.

**후보는 디코더 그래프에서 꺼냅니다.** SAM 은 원래 크기가 다른 해석을 네 개 만들고 그중 하나를
스스로 고릅니다. 정석은 `return_single_mask=False` 로 다시 내보내는 것이지만 torch 와 MobileSAM
패키지가 필요합니다. 고르기 직전 지점을 ONNX 출력으로 노출하기만 하면 같은 값을 얻고,
가중치를 건드리지 않으므로 결과도 같습니다. 저해상도 마스크를 화면 좌표로 올리는 일은 서버가
공식 `mask_postprocessing` 과 같은 계산으로 합니다.

**클릭한 자리를 담은 덩어리를 고릅니다.** 처음에는 가장 큰 덩어리를 골랐는데, 배경 점이 긴 물체를
두 조각으로 끊으면 사용자가 실제로 집은 조각이 작다는 이유로 버려졌습니다. 클릭한 점이 결과 밖에
있는 것은 사용자가 이해할 수 없는 동작이라 규칙을 바꿨습니다.

**사전 라벨링 추론은 워커가 아니라 서버가 돌립니다.** 학습은 GPU 와 파이썬이 필요해 워커의 몫이지만,
추론은 ONNX Runtime 하나면 되고 서버는 SAM 보조 때문에 이미 그것을 들고 있습니다.
작업 큐·데이터셋 동기화·아티팩트 왕복을 한 벌 더 만드는 대신 있는 것으로 끝냅니다.
사진 수백 장이면 몇십 초라, 한 번에 볼 장 수만 나눠 부르면 됩니다.

**임베딩은 메모리에만 캐시합니다.** 인코더는 사진당 한 번이면 되고 디코더는 그 수백 분의 일입니다.
그래서 사진 해시로 임베딩을 몇 장 들고 있습니다. 디스크에 두면 한 장에 4MB 라
사진 만 장이면 40GB 가 되는데, 그만큼을 아끼자고 정리 정책을 하나 더 만들 이유가 없습니다.
라벨링 화면은 사진을 열 때 미리 인코더를 돌려 두어 첫 클릭이 기다리지 않게 합니다.

**마스크에서 폴리곤을 뽑는 일은 직접 구현했습니다.** WPF 쪽은 OpenCV 의 FindContours 를 쓰지만
이 서버는 이미지 처리를 SkiaSharp 로만 하고 OpenCV 네이티브를 들이지 않습니다.
필요한 것은 "가장 큰 덩어리의 바깥 윤곽" 하나뿐이라, 연결 요소 라벨링 → Moore 경계 추적 →
Douglas-Peucker 단순화를 순수 C# 으로 두고 시험으로 지킵니다.

**타일 피라미드를 두지 않았습니다.** 설계 문서가 상정한 2448×2048 급은 JPEG 축소본 한 장이면
화면 전체를 덮고, 확대할 때만 원본으로 바꾸면 됩니다. 타일은 저장 용량과 생성 비용이 큰 대신
이 해상도에서는 이득이 없습니다. 훨씬 큰 이미지가 들어오면 그때 축소본 위에 얹으면 됩니다.

**캔버스는 TypeScript 대신 ES 모듈로 썼습니다.** .NET 빌드에 npm 과 tsc 단계를 더하면
MSI 패키징과 폐쇄망 배포가 그만큼 복잡해집니다. 커지면 그때 빌드 단계를 붙이면 됩니다.

**이미지는 쿠키로 인증합니다.** 브라우저의 img 태그는 Authorization 헤더를 붙일 수 없습니다.
토큰을 URL 에 넣으면 접근 로그와 방문 기록에 남으므로, 이미지 경로에만 쓰이는
HttpOnly·SameSite=Strict 쿠키를 로그인 때 한 번 내려 줍니다.

**클래스 선택은 다음에 그릴 것만 정합니다.** 선택된 라벨의 클래스까지 함께 바꾸면,
방금 그린 박스가 선택된 채로 남아 있다가 다음 클래스를 고르는 순간 조용히 바뀝니다.
이미 붙은 라벨의 클래스는 목록에서 명시적으로 고를 때만 바뀝니다.

## 인증과 역할

토큰 세 종류를 `Authorization` 헤더 접두사로 구분합니다. 사용자 JWT, `wk_` 로 시작하는 워커 서비스 계정 토큰,
`ln_` 로 시작하는 라인 PC 서비스 계정 토큰입니다.

라인 PC 는 사람이 아니라 로그인 화면을 거칠 수 없습니다. 그렇다고 워커 토큰을 주면 학습 큐와
아티팩트 업로드까지 열리므로, 같은 방식이되 범위가 다른 토큰을 따로 둡니다.
라인 토큰이 할 수 있는 일은 셋입니다 — 모델 참조 해석, 아티팩트 내려받기, NG 사진 올리기.
토큰 원문은 발급 응답에서 한 번만 나가고 서버에는 SHA-256 해시만 남습니다.
관리자가 비활성하면 인증 단계에서 막히므로 "이 라인을 끊었다" 는 조치가 실제로 성립합니다.
워커 토큰은 서버에 SHA-256 해시로만 저장되고, 발급 응답에서 한 번만 노출됩니다.

| 역할 | 할 수 있는 일 |
|---|---|
| Viewer | 조회 |
| Labeler | 조회 + 라벨 (Phase 4 용, 현재 미사용) |
| Engineer | 모델·버전 등록, Staging 승격, 바인딩, 학습 작업 생성 |
| Admin | Production·Retired 승격, 워커 발급·비활성, 사전학습 미러 관리 |
| Worker | 워커 프로토콜, 데이터셋 export, 사전학습 다운로드, 아티팩트 업로드 |
| Line | 모델 참조 해석, 아티팩트 다운로드, 동기화 페이로드 |

## 모델 레지스트리 (Phase 1)

업로드는 스트리밍 저장과 SHA-256 계산으로 시작해, 같은 계열에 같은 파일이면 기존 버전을 그대로 돌려줍니다.
그다음 `InferenceSession` 을 만들지 않고 protobuf 만 읽어 규약을 판별하고, 클래스 목록과 입력 크기를 확인합니다.
`names` 가 없으면 업로드 폼의 클래스를 요구하고, 모델 계열의 클래스와 순서까지 어긋나면 거부합니다.
YOLO 파생 모델은 라이선스 필드가 없으면 등록되지 않고, Production 승격에는 Admin 의 라이선스 확인이 더 필요합니다.

스테이지는 Candidate에서 Staging, Production, Retired 순으로 이동합니다. Production 은 모델 계열당 하나뿐이라,
새 버전이 올라오면 이전 Production 은 Staging 으로 내려갑니다. 롤백은 바인딩 이력에서 이전 버전을 고르는 것으로 끝납니다.

레시피 도구에는 `model://{modelId}@{version}` 또는 `model://{modelId}@production` 참조를 저장합니다.
라인 PC 는 동기화 페이로드에 실린 sha256 으로 아티팩트를 미리 받아 두고, 서버가 없어도 캐시로 검사를 계속합니다.
아티팩트 응답의 ETag 가 sha256 이라 두 번째 요청부터는 304 로 끝납니다.

### 상위 설계 문서와 다른 점

ONNX 해시의 유일 범위를 전역이 아니라 모델 계열 안으로 좁혔습니다.
전역 유일로 두면 다른 계열에 같은 파일을 올렸을 때 남의 계열 버전이 반환되어 정보가 새고,
그 계열의 작업 유형·클래스 검증도 건너뛰게 됩니다. 아티팩트 파일 자체는 여전히 sha 경로로 한 벌만 저장합니다.

### VMS 리포에 필요한 후속 조치

`VMS.Core.Contracts` 의 `OnnxMetadataReader` 는 protobuf 길이 필드를 남은 바이트와 대조하지 않습니다.
조작된 varint 하나로 스트림이 뒤로 감겨 파싱이 무한히 반복되므로, 신뢰할 수 없는 파일에 쓰면 요청 하나가 스레드를 영구 점유합니다.
이 리포는 자체 `OnnxSafeReader` 로 우회했고, VMS 리포도 같은 하한 검사를 넣었습니다 (VMS PR #445, 2026-09-09 —
`VMS.Core.Contracts` 1.33 이후 패키지부터 반영. 그 전 패키지의 경로 API 는 여전히 부르지 마세요).

## 학습 워커 (Phase 3)

워커는 서버로만 아웃바운드 HTTP 를 열기 때문에 방화벽 예외가 필요 없습니다. 서버는 워커 주소를 모릅니다.

시작할 때 venv 를 만들고 허용 목록(`scripts/requirements-allowlist.txt`) 안의 패키지만 설치한 뒤,
`worker_diag.py` 로 GPU·CUDA·패키지 버전을 확인해 서버에 보고합니다. 진단에 실패하면 서버가 워커를 비활성으로 두고
작업을 주지 않습니다. 프로토콜 버전이 서버와 다를 때도 마찬가지입니다.

작업을 받으면 데이터셋 zip 을 내려받아 경로 탈출과 심볼릭 링크를 막으며 풀고, 사전학습 가중치는 서버 미러에서만 받습니다.
스크립트는 서버 매니페스트의 해시와 일치할 때만 실행합니다. 하이퍼파라미터는 서버와 워커가 같은 화이트리스트로
두 번 검증하고, `ProcessStartInfo.ArgumentList` 로만 넘겨 문자열 연결을 하지 않습니다.

실행 중에는 stdout 프로토콜을 읽어 1초 단위로 진행률과 로그를 보고합니다.
`[EPOCH]` 나 `[PROGRESS]` 가 30분간 없으면 프로세스 트리를 종료하고, 전체 24시간 상한도 겁니다.
로그에서 CUDA 메모리 부족이 보이면 batch 를 절반으로 줄여 한 번 다시 돌립니다.
끝나면 `best.onnx` 를 Phase 1 검증 파이프라인에 태워 Candidate 버전으로 등록하고,
데이터셋 해시·스크립트 해시·패키지 목록·seed 를 재현성 레코드로 남깁니다.

상태는 서버가 소유합니다. 워커는 보고만 하고, 전이 규칙은 서버가 검증합니다.

```
Queued → Assigned → Preparing → Running → Exporting → Uploading → Succeeded
```

배정 후 60초 안에 ack 이 없거나 하트비트가 90초간 끊기면 서버가 작업을 다시 큐에 넣습니다.
재시도 한도를 넘기면 실패로 확정합니다. 스크립트 오류는 같은 입력이면 같은 결과이므로 재시도하지 않습니다.

## 라인 모니터링 (Phase 5)

배포한 모델이 라인에서 실제로 어떻게 하고 있는지 봅니다. 화면은 `/monitoring` 입니다.

**이어지는 길.** VMS 가 검사마다 `mv:{모델버전id}` 를 실어 운영 웹에 보내고, 운영 웹이
`GET /api/history/model-outcomes` 로 모델 버전별 집계를 냅니다. MLOps 가 그것을 당겨 와
최근 구간(기본 7일)과 기준 구간(그 앞 21일)을 견줍니다. **당겨 오는 쪽입니다** —
운영 웹에 MLOps 를 위한 쓰기 경로를 만들지 않았습니다. 그쪽은 멈추면 안 되는 시스템이라
MLOps 가 그 위에 얹히지 않게 했습니다.

**판단.** 규칙은 `Core/Monitoring/ModelHealth.cs` 한 곳에 있습니다.

| 신호 | 언제 | 재학습 권고 |
|---|---|---|
| 판단 보류 | 구간 하나라도 100건 미만 | 아니오 — "괜찮다" 가 아니라 "아직 모른다" |
| 입력 변화 | 밝기·선명도가 기준 대비 20% 넘게 움직임 | 아니오 — 조명·초점·렌즈를 먼저 |
| 불량률 상승 | 2%p 넘게 오르고 두 비율 z 검정 p < 0.01 | 예 |
| 신뢰도 하락 | DL 신뢰도 평균이 10% 넘게 내려감 | 예 |
| 이상 없음 | 위 어디에도 걸리지 않음 | 아니오 |

순서가 있습니다. 입력이 달라졌으면 그것부터 말합니다 — 재학습해도 낫지 않기 때문입니다.
불량률만 보고 울리지 않고 통계적 유의성을 함께 보는 이유는, 표본이 적을 때 헛경고가 몇 번 나면
사람이 경고를 통째로 무시하게 되기 때문입니다.

**재학습.** 권고가 붙은 줄의 [재학습] 은 그 버전을 만든 학습 작업의 설정 그대로 제출 창을 채웁니다.
**데이터셋 버전만 비워 둡니다** — 같은 판으로 다시 돌리면 같은 모델이 나오므로 새 사진이 담긴 판을
사람이 골라야 합니다. 밖에서 올린 모델은 되풀이할 설정이 없어 버튼 대신 그 이유가 나옵니다.
학습을 자동으로 걸지 않고, 모델을 자동으로 내리지도 않습니다.

**설정.** `Monitoring:ProductionWebUrl` 이 비면 기능이 꺼지고 화면이 그 이유를 말합니다.
운영 웹과 같은 `Jwt:Key`·`Jwt:Issuer` 를 써야 토큰이 통합니다. **audience 는 다릅니다** —
운영 웹은 `BODA.VMS.Web.Client` 를 검증하므로 `Monitoring:Audience` 가 그 값입니다.
나가는 토큰의 역할은 `Viewer` 하나입니다.

**이어지지 않은 검사.** 옛 형식 식별자나 DL 을 안 쓴 스텝은 버리지 않고 세어서 함께 냅니다.
그 수가 크면 라인이 아직 옛 VMS 를 쓰고 있다는 뜻이라 그 자체가 알아야 할 정보입니다.

### 자동과 승인의 경계

라인이 NG 사진 전부와 양품 1/200 을 스스로 올리므로 데이터는 사람 손 없이 쌓입니다.
그 위에 두는 경계를 이렇게 정했습니다.

| 단계 | 자동 | 사람 |
|---|---|---|
| 수집 · 품질 지표 재기 · 중복 제거 | 자동 | |
| 사전 라벨(Active Learning 미리 채우기) | 자동 | 검토·확정은 사람 |
| 데이터셋 판(스냅샷) 뜨기 | 자동 | 어느 데이터로 돌릴지는 사람이 고름 |
| 학습 작업 제출 → Candidate 등록 | 자동 | 시작은 사람의 [재학습] 한 번 |
| Staging · Production 승격, 롤백 | | **항상 사람** |
| 재학습 권고 | 자동으로 띄움 | 받아들일지는 사람 |

원칙은 둘입니다. **라인에 나가는 결정은 자동화하지 않습니다.**
그리고 **학습에 무엇이 들어가는지도 사람이 정합니다** — 그래서 재학습 창이 뜨는 판은
기본으로 `ReviewedOnly` 입니다. 검토하지 않은 사전 라벨을 학습에 흘리면,
그 오염은 모델이 라인에서 이상하게 굴 때에야 드러납니다.

그 사이의 기계적인 단계는 [재학습] 한 번으로 이어집니다 — 판 뜨기 → 제출 → Candidate 등록.
데이터 임계치에 닿으면 사람 없이 도는 완전 자동 재학습은 넣지 않았습니다. 이 1차 템플릿이
몇 사이클 돌아 후보 모델 품질과 데이터 품질 필터를 믿을 수 있게 된 뒤에 볼 일입니다.

## API

전체 목록은 개발 모드의 Swagger(`/swagger`)에 있습니다. 주요 경로만 적습니다.

| 경로 | 용도 |
|---|---|
| `POST /api/models`, `POST /api/models/{id}/versions` | 모델 계열 생성, ONNX 업로드 |
| `POST /api/model-versions/{id}/promote` | 스테이지 승격·강등 |
| `GET /api/model-versions/{id}/artifact` | 아티팩트 다운로드 (ETag = sha256) |
| `GET /api/models/{id}/resolve?stage=production` | 라인 PC 의 참조 해석 |
| `PUT /api/recipes/{recipeId}/tools/{toolId}/model` | 바인딩 |
| `POST /api/model-bindings/{id}/rollback` | 롤백 |
| `GET /api/recipes/{recipeId}/model-bindings/payload` | 동기화 페이로드 (VMS 프리페치) |
| `POST /api/workers`, `POST /api/workers/register` | 워커 발급(Admin), 워커 등록 |
| `POST /api/training-jobs` | 학습 작업 생성 |
| `GET /api/training-jobs/next?wait=25` | 워커 long-poll |
| `PATCH /api/training-jobs/{id}/progress` | 진행률·로그 보고 |
| `POST /api/training-jobs/{id}/artifacts` | 아티팩트 업로드 → Candidate 생성 |
| `GET /api/pretrained/{ref}/{file}` | 사전학습 미러 |
| `GET /api/sam/status` | SAM 보조를 쓸 수 있는지 (화면이 버튼을 보일지 정함) |
| `POST /api/sam/prepare` | 임베딩 미리 만들기 (사진을 열 때) |
| `POST /api/sam/predict` | 클릭 점들 → 크기가 다른 폴리곤 후보들 |
| `POST /api/images/line-ng` | 라인 PC 의 NG 이미지 수집 (출처·라인 고정) |
| `POST /api/datasets/{id}/prelabel` | 후보 모델을 돌려 초기 라벨·불확실도 채우기 (§5.4) |
| `POST /api/datasets/{id}/prefill` | 바깥에서 만든 예측·불확실도를 그대로 넣기 |
| `POST /api/line-clients` | 라인 PC 서비스 계정 발급 (Admin) · 화면은 /line-clients |
| `GET /api/monitoring/models` | 라인에 나간 모델의 상태 (Phase 5) |
| SignalR `/hubs/models`, `/hubs/training` | 버전·바인딩 변경, 진행률·로그 중계 |

오류는 항상 `{"code": "...", "message": "...", "details": [...]}` 형태입니다.
`code` 는 `ClassMismatch`, `MissingNames`, `LicenseRequired`, `InvalidStageTransition`, `DuplicateJob` 등입니다.
응답의 열거형은 camelCase 이고, 그 값을 그대로 URL 에 되돌려 넣어도 동작합니다.

299개가 GPU 없이 몇 초 만에 끝납니다. 규약 판별은 VMS 리포와 같은 스텁 ONNX 를 씁니다.
워커 경로는 `scripts/train_fake.py` 가 stdout 프로토콜만 흉내 내며 정상·오류·무응답·취소·OOM 상황을 만들어 줍니다.
E2E 테스트는 인메모리 서버에 실제 `JobRunner` 를 붙여 작업 제출부터 Candidate 등록까지 한 번에 확인합니다.
데이터 관리 쪽은 실제로 디코딩되는 PNG 를 만들어 업로드부터 내보내기 zip 까지 돌리고, zip 을 열어 구조를 확인합니다.
파이썬이 없는 PC 에서는 워커 프로세스 테스트가 조용히 통과합니다.
사전 라벨링은 좌표 규약(레터박스)·NMS·불확실도를 모델 없이 확인하고, 실제 학습된 검출 모델이 있는 PC 에서는
그 모델로 돌려 붙은 상자가 사진 안에 들어오는지까지 봅니다 (`MLOPS_TEST_DETECTOR`·`MLOPS_TEST_IMAGE`).
모니터링은 운영 웹 자리에 가짜를 세워, 라인 여러 줄이 한 모델로 합쳐지는지·옛 형식이 세어지는지·
나가는 토큰이 그쪽 audience 와 읽기 역할 하나인지를 봅니다.
SAM 은 마스크에서 폴리곤을 뽑는 순수 부분(좌표 규약·윤곽 추적·확대·덩어리 선택)을 모델 없이 확인하고,
모델 파일이 있는 PC 에서는 실제 추론까지 돌립니다 — 클릭한 자리에 폴리곤이 생기는지, 두 객체를 갈라 잡는지,
후보가 크기 순으로 여러 개 나오는지, 배경 점이 실제로 듣는지, 가려져 조각난 물체에서 클릭한 조각이 나오는지.

## 남은 일

굵은 것부터 적었습니다. 각 항목 뒤는 지금 어디까지 있는지입니다.

**VMS 리포 연동 — 한 바퀴가 닫혔습니다.** 모델과 데이터가 양쪽으로 오갑니다.

| 길 | 어디 | 상태 |
|---|---|---|
| 모델 받아 쓰기 (`model://` 해석·캐시·엔진 적재) | VisionSetup·라인 PC | VMS master (PR #437·#438) |
| 모델 올리기 ([레지스트리에 등록]) | AI 학습 도구 | VMS master (PR #439) |
| 데이터셋 받기 ([웹 데이터셋 내려받기]) | AI 학습 도구 | VMS master (PR #440) |
| 세그멘테이션 학습·추론 (`rfdetrseg`) | 학습 스크립트 · VisionSetup 도구 | VMS master (PR #441·#442) |

넷 다 아직 릴리즈 전이고 다음 주간 릴리즈에 실립니다.

레시피가 `model://{modelId}@{version|stage}` 로 모델을 가리키면 라인 PC 가 라인 토큰으로
참조를 풀어 아티팩트를 해시 이름의 로컬 캐시에 받습니다. 검사 경로는 네트워크를 쓰지 않고
캐시만 봅니다.

올리는 쪽은 사람의 웹 계정 JWT 로 올립니다 — 라인 토큰은 받아 가는 쪽 자격이라 등록에
쓰지 않습니다. 올라간 버전은 Candidate 로 들어가 승격 전에는 라인에 나가지 않습니다.

데이터셋은 판(스냅샷)을 골라 내보내기 폴더로 받고, 그것이 학습 데이터셋 경로가 됩니다.
라벨을 학습 도구 형식으로 되돌리지는 않습니다 — 웹에서 라벨링한 것은 웹이 정본입니다.

셋 다 살아 있는 서버에 붙여 확인했습니다.

**완전 자동 재학습.** 1차 파이프라인([재학습] 한 번 → 판 뜨기 → 제출 → Candidate)은 들어갔습니다.
데이터가 얼마쯤 쌓이면 사람 없이 도는 단계는 넣지 않았습니다 — 위 "자동과 승인의 경계" 를 보세요.
몇 사이클 돌려 후보 모델 품질과 데이터 품질 필터를 믿을 수 있게 된 뒤에 볼 일입니다.

**라인 NG 이미지의 보내는 쪽.** 받는 쪽은 열렸습니다 — `POST /api/images/line-ng` 로
라인 계정(`Line` 역할)이 NG 사진을 올리면 출처가 `lineNg` 로 고정되고 `inspectionId` 로
생산 이력과 이어집니다. 라인 계정에 태그·삭제 권한은 주지 않습니다.
VMS 쪽 송신부는 닫혔습니다 (VMS PR #446 — 이미지 저장 설정의 [NG 이미지 MLOps 전송] + 양품 1/N 샘플, 기본 1/200).
라인 토큰으로 오는 요청은 `lineId` 를 토큰에서 읽으므로 VMS 는 라인 이름을 보내지 않습니다.

**워커 설치 패키지.** MSI(WiX) 프로젝트가 없습니다. 워커는 오프라인 wheel 폴더를 쓸 수 있지만
(`Worker:WheelBundleDir` → `pip --no-index --find-links`), 그 번들을 만드는 단계가 없습니다.

**보존 정책.** 오래된 이미지를 자동으로 지우는 규칙이 없습니다. 품질 지표는 재어 두었으니
"흐린 것부터 골라 보고 사람이 지우는" 길은 열렸지만, 자동 삭제는 되돌릴 수 없어 넣지 않았습니다.
무엇을 얼마나 오래 두는지는 운영이 정할 일입니다.

**작은 것들.**
- 데이터셋 내보내기를 매니페스트 기반으로 바꿔 바뀐 파일만 받기
  (지금도 Range 요청과 ETag 를 지원해 이어받기는 됩니다. 수십 GB 에서 zip 을 통째로 다시 만드는 것이 문제입니다.)
- OCR venv 분리 검토
