# 로컬 계정 로그인 설계 메모 (`Auth:Mode`)

**상태: 제안. 구현 전입니다.** 2026-09-21 에 적었습니다.
정해진 것이 아니라 "이렇게 하면 이런 대가를 치른다" 를 적어 둔 것입니다.

## 왜 이 메모가 있나

지금 사람의 인증은 운영 웹(BODA.VMS.Web)이 합니다. 브라우저가 아이디·비밀번호를 그쪽에 직접 보내고,
받은 JWT 를 우리가 서명·발급자·audience 로 검증합니다. 비밀번호는 이 서버를 지나가지 않습니다.

그래서 **운영 웹이 없는 설치에서는 사람이 들어올 길이 없습니다.** 지금 대비는 설치 가이드의 뒷길
하나뿐입니다 — 같은 키로 HS256 토큰을 손으로 만들어 붙여넣기. 시험용으로 적어 둔 것이지
고객에게 시킬 절차가 아닙니다. MLOps 만 따로 놓는 설치(오프라인 학습 서버, 운영 웹을 쓰지 않는 현장)가
실제로 있을 수 있으므로, 그 자리를 메우는 설계를 적어 둡니다.

## 지금 운영 웹에 매인 곳은 한 군데입니다

| 기능 | 운영 웹 의존 | 웹이 죽으면 |
|---|---|---|
| 사람 로그인 | **있음** | 새로 들어올 수 없음 |
| 끊긴 토큰 확인 | 약함 | 통과시킴 (`WebTokenRevocationClient`) |
| 역할·인가 | 없음 | `Members` 표가 여기서 정함 |
| 워커·라인 토큰 | 없음 | 그대로 |
| 레지스트리·데이터셋·라벨링·학습 | 없음 | 그대로 |
| 라인 모니터링 | 있음 | 그 화면만 "볼 수 없음" |

**즉 메워야 하는 구멍은 "사람이 처음 들어오는 것" 하나입니다.** 나머지는 이미 따로 섭니다.

## 규약 (제안)

**1. 모드는 배타적입니다.** `Auth:Mode` 는 `Web`(기본) 또는 `Local` 입니다. 둘 다 허용하지 않습니다.
`Members` 는 username 이 키라, 같은 이름이 두 출처에서 들어오면 어느 쪽이 그 사람인지 아무도 모릅니다.
한 서버는 한 가지 방법으로만 사람을 들입니다.

**2. 역할 사다리와 `Members` 표는 그대로 씁니다.** 모드가 바뀌어도 "이 계정이 MLOps 에서 무엇을 할 수 있나" 는
같은 표가 정합니다 (개발 문서 §6). 로컬 모드는 그 표에 비밀번호 열이 붙을 뿐입니다.
`Web` 모드에서 그 열들은 전부 비어 있습니다.

**3. 비밀번호 해시는 직접 만들지 않습니다.** `PasswordHasher<T>`(ASP.NET Core Identity, PBKDF2)를 씁니다.
반복 횟수·솔트·업그레이드 규칙이 이미 들어 있고, 우리가 암호를 설계할 이유가 없습니다.

**4. 로컬 토큰에 `mlops:self` 를 붙이지 않습니다. ← 여기가 함정입니다.**
`ServiceTokenIssuer` 가 발급하는 토큰에는 `mlops:self` 표시가 붙고, `MemberRoleClaimsTransformation` 은
그 표시를 보면 **역할 표를 적용하지 않습니다**. 개발·서비스 토큰은 실린 역할이 곧 의도여서 맞는 규칙이지만,
로컬 로그인 토큰에 그대로 쓰면 **표에서 강등하거나 계정을 비활성해도 토큰 수명(8시간) 동안 듣지 않습니다.**
로컬 로그인은 표가 정본이어야 하므로 이 표시를 쓰지 않고, 변환을 그대로 받습니다.

**5. 그 대신 발급자로 가릅니다 — 안 가르면 로컬 로그인이 전부 끊깁니다.**
`WebTokenRevocationClient` 는 받은 토큰을 운영 웹 `/api/auth/me` 에 들려 보내 **401 이면 끊습니다.**
운영 웹은 우리 로컬 계정을 모르므로 401 을 줍니다. 그런데 이 검사는 `Monitoring:ProductionWebUrl` 만
있으면 켜집니다 — **로컬 모드인데 모니터링을 쓰는 설치에서, 로그인한 사람이 전원 60초 안에 쫓겨납니다.**
그러므로 로컬 발급자(`Auth:Local:Issuer`)로 발급하고, 그 발급자의 토큰에는 묻지 않습니다.
`Auth:Mode=Local` 이면 검사 자체를 끄는 것도 같이 둡니다 (두 겹).

**6. 서명 키를 분리합니다.** 지금 `Jwt:Key` 는 "운영 웹과 같아야 하는 값" 입니다. 로컬 모드의 발급·검증은
`Auth:Local:Key` 로 따로 둡니다. 로컬 모드에서도 `Jwt:*` 는 남습니다 — 모니터링이 운영 웹으로 나갈 때
그 키로 발급하기 때문입니다 (`Monitoring:Audience`). 두 키가 섞이면, 우리가 발급한 토큰이 운영 웹에서도
통할 여지를 스스로 만드는 셈입니다.

**7. 시도 제한과 감사를 함께 넣습니다.** 계정 잠금(연속 실패 N회 → M분)과 IP 단위 제한, 그리고
로그인 성공·실패·비밀번호 변경·관리자 초기화를 기록합니다. 비밀번호를 들고 있기로 한 이상
"누가 언제 틀렸나" 를 말할 수 없으면 안 됩니다.

## 데이터 모델

`Member` 에 붙는 열입니다. 표를 새로 만들지 않습니다.

| 열 | 뜻 | `Web` 모드 |
|---|---|---|
| `PasswordHash` | PBKDF2 해시 (형식은 `PasswordHasher` 가 정함) | null |
| `PasswordUpdatedAt` | 마지막으로 바꾼 시각 | null |
| `MustChangePassword` | 임시 비밀번호 상태 — 바꾸기 전에는 다른 화면에 못 들어감 | false |
| `Disabled` | 비활성. 역할 변환 단계에서 막으므로 **즉시 듣습니다** | false |
| `FailedCount` · `LockedUntil` | 연속 실패와 잠금 해제 시각 | 0 · null |

`Disabled` 를 인증이 아니라 **역할 변환 단계**에서 보는 이유는, 그 자리가 이미 요청마다 도는 캐시이고
`Invalidate` 로 즉시 버릴 수 있기 때문입니다 — 권한 회수가 늦으면 안 된다는 기존 규약과 같은 자리입니다.

## 엔드포인트

| 엔드포인트 | 누가 | 비고 |
|---|---|---|
| `GET /api/auth/mode` | 익명 | 로그인 화면이 무엇을 그릴지 정함. 지금 `/auth/web-login` 을 흡수 |
| `POST /api/auth/login` | 익명 | **`Local` 모드에서만** 열림. `Web` 모드에서는 404 |
| `POST /api/auth/change-password` | 본인 | 임시 비밀번호 해제 통로 |
| `POST /api/members/{id}/reset-password` | Admin | 임시 비밀번호를 만들어 **응답에 한 번만** 보여 줌 |
| `POST /api/members` | Admin | 계정 만들기 (지금의 역할 부여에 비밀번호가 붙음) |

`Web` 모드에서 로컬 `login` 을 404 로 두는 것은 규약 1의 연장입니다. 열려 있으면 "이 서버의 계정" 이
두 뜻을 갖습니다.

## 토큰

1단계는 **8시간 단일 토큰**입니다. "로그인 유지"(refresh 토큰)는 웹 모드에만 두고, 로컬 모드는
나중에 필요해지면 봅니다 — refresh 를 넣는 순간 회전·재사용 탐지·저장 위치가 따라옵니다.

## 화면

- `Login.razor` (189줄)는 `GET /api/auth/mode` 로 갈라집니다. `Local` 이면 우리 API 로 보내고,
  운영 웹 관련 안내(CORS 실패 구분, "서버는 운영 웹에 닿습니다")는 감춥니다.
- 비밀번호 변경 화면 하나. `MustChangePassword` 면 다른 화면으로 못 갑니다.
- 관리 ▸ 사용자 역할에 계정 만들기·임시 비밀번호 발급·비활성이 붙습니다.

## 설치

- `install-server-service.ps1` 에 `-Local` 스위치: `Auth:Mode=Local`, 로컬 서명 키 생성(서비스 환경변수),
  첫 관리자 계정과 임시 비밀번호를 **한 번만** 출력합니다. 지금의 손수 JWT 뒷길을 없앱니다.
- `Web` 모드 설치는 지금 그대로입니다 (운영 웹 `Cors:AllowedOrigins` 안내 포함 — 설치 가이드 3.4).
- 설치 가이드(`docs/manual/install.json`)에 모드 표를 넣습니다. 스크립트를 고치면 그 json 을 함께 고칩니다.

## 시험 (최소)

- `Local` 모드: 맞는 비밀번호로 200, 틀리면 401, N회 연속 실패 뒤 잠금, 잠금 해제 시각 이후 통과
- `Web` 모드에서 `POST /api/auth/login` 이 404
- 로컬 토큰이 **역할 변환을 받는다** (표에서 강등하면 다음 요청부터 듣는다)
- 로컬 토큰에 **취소 검사를 하지 않는다** — 모니터링이 켜진 로컬 모드에서 로그인이 유지되는지 (규약 5)
- `Disabled` 계정은 토큰이 살아 있어도 즉시 막힌다
- `MustChangePassword` 상태로는 다른 API 에 못 들어간다
- 비밀번호 변경 뒤 옛 비밀번호로 401
- 관리자 초기화가 임시 비밀번호를 한 번만 돌려준다
- 워커·라인 토큰은 두 모드 모두에서 영향을 받지 않는다 (`WorkerScopeTests` 와 같은 경계)

## 1단계에서 하지 않을 것

- **하이브리드 모드** (규약 1)
- 비밀번호 복잡도·만료 정책, 2단계 인증, SSO
- 로컬 모드의 "로그인 유지"(refresh)
- 이메일로 비밀번호 찾기 — 폐쇄망이라 메일이 나가지 않습니다. 관리자 초기화가 그 자리입니다.

## 열린 질문

- **로컬 서명 키를 어디에 두나.** 서비스 환경변수(지금 `Jwt__Key` 와 같은 방식)가 무난하지만,
  키를 잃으면 모두가 다시 로그인해야 합니다. `DataDir` 에 DPAPI 로 봉해 두는 방법도 있습니다.
- **`Web` → `Local` 전환.** 기존 `Members` 행에는 비밀번호가 없습니다. 관리자가 전원 초기화하는 것 외에
  길이 없고, 그 관리자 자신은 부트스트랩으로 들어와야 합니다.
- **계정 살림을 운영이 감당할 수 있나.** 라벨러가 수십 명이면 발급·분실·퇴사자 회수가 전부 이쪽 일이 됩니다.
  운영 웹이 있는 현장에서 `Local` 을 고를 이유는 없다고 봅니다.

## 요약 의견

**"따로 설 수 있어야 한다" 는 맞고, "따로 살림을 차리는 것" 이 기본값이어서는 안 됩니다.**
운영 웹이 있는 설치는 계정이 한 곳에 있는 편이 낫습니다 — 퇴사자를 한 번만 지우면 되고,
비밀번호 보관 책임도 인증 범위 안에 남습니다. `Local` 은 운영 웹이 없는 설치를 위한 두 번째 문입니다.
